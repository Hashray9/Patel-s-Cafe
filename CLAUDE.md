# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A multi-tenant cafe/restaurant management PWA ("Patel's Cafe" is the first tenant). Every cafe is fully isolated and has its own tables, menu, orders, settings and staff. Each cafe has three roles:
- **owner**: everything, including staff management, store settings, table add/remove and data resets
- **counter**: floor plan, orders, menu and reports
- **cook**: the kitchen display only

Stack: React 19 + TypeScript + Vite 8 + Tailwind v4 frontend, an API that runs as a **Cloudflare Worker** (Hono) in `server/`, and Supabase for Postgres, Auth and Realtime.

## Commands

Frontend (repo root):
- `npm run dev`: Vite dev server
- `npm run build`: `tsc -b && vite build`. Type errors fail the build, and `noUnusedLocals`/`noUnusedParameters` are on.
- `npm run lint`: ESLint (typescript-eslint, react-hooks including the React Compiler rules, react-refresh)

API (`cd server`):
- `npm run dev`: `wrangler dev` on port 5000, which is the frontend's fallback `VITE_API_URL`
- `npm run deploy`: `wrangler deploy` (production: `patels-cafe-api.<account>.workers.dev`)
- `npm run check`: bundle dry-run, a quick syntax and import check

There is no test suite.

Environment:
- Root `.env`: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_API_URL`. It currently points at the **production** Worker. Override it in `.env.local` to use a local API.
- `server/.dev.vars` (git-ignored, see `.dev.vars.example`): `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`. In production these are set with `wrangler secret put`. The optional vars `APP_URL` (link target in invite emails) and `ALLOWED_ORIGINS` (CORS allow-list) are documented in `wrangler.toml`.

## Architecture

### Tenancy and security model (read this before touching data access)
- The browser uses Supabase directly only for **auth** and **Realtime**. Every read and write goes through the Worker API with `Authorization: Bearer <supabase access_token>`.
- The Worker verifies the token, then loads the caller's **single** membership row from `user_roles` (`user_id` is UNIQUE, so one cafe per account). That row is the **only** source of `cafeId` and `role`. Never take a cafe id from the request.
- The Worker uses the service-role key, which **bypasses RLS**. Every query must therefore include `.eq('cafe_id', cafeId)`, and every id from the URL or body must be re-checked against that cafe. Helpers such as `getOrderOr404` and `getTableOr404` exist for this.
- Route guards: `anyMember`, `staff` (owner + counter) and `ownerOnly`. Cooks can only `PUT /api/orders/:id` with status `preparing`/`ready`.
- RLS in Postgres allows signed-in users to **SELECT their own cafe's rows only** (`my_cafe_id()`), and there are no client write policies.
- **Realtime is Broadcast, not Postgres Changes.** The trigger `broadcast_cafe_change` (migration 005) sends one `change` message per row change on `orders`, `tables`, `menu_items` and `settings` to the **private** topic `cafe:<cafe_id>`. Order messages carry the full row. An RLS policy on `realtime.messages` lets a user join only `'cafe:' || my_cafe_id()`, and "Allow public access" is off in the dashboard's Realtime settings. Clients use `src/hooks/useCafeLive.ts`, which handles the channel, the live status, resync on (re)subscribe and wake-up, and fallback polling.
- Order totals are **computed on the server** (`priceOrder`) from the cafe's menu prices and tax rate. Client-sent totals are ignored.

### Onboarding flows
- **New cafe:** Login → "Register your cafe" → `supabase.auth.signUp` stores `cafe_name` in user metadata. After the first sign-in the account has no membership, so `App.tsx` shows `CreateCafe`, which calls `POST /api/cafes`. That calls the `create_cafe` SQL function, which atomically creates the cafe, its settings row and an owner membership.
- **Staff:** an owner uses Settings → Staff (`StaffManager`) → `POST /api/staff {email, role}`.
  - New email: `inviteUserByEmail` sends an invite. The link lands with `type=invite`, and `AuthContext` routes it to `ResetPassword` so the person can set a password.
  - Existing account with no cafe: linked immediately.
  - Account that already belongs to a cafe: rejected.
- Routing in `App.tsx` `MainApp`: loading → recovery/invite link → `ResetPassword` → no session → `Login` → membership error → retry screen → no cafe → `CreateCafe` → cook → `CookDashboard` → otherwise `CafeProvider` + `DashboardContent`. Owner-only Settings sections are gated by `isOwner`.

### Data model conventions
- The DB uses snake_case and the API/frontend use camelCase. Mappers (`toTable`, `toOrder`, …) sit at the top of `server/worker.js`. `orderFromRow` in `src/hooks/useCafeLive.ts` mirrors `toOrder` for live order rows. A new column has to be added to the mapper(s), the validation, `src/types.ts` and the SQL.
- IDs are text with a prefix and a UUID, generated by the server: `cafe-`, `t-`, `m-`, `ord-`, `g-`. Timestamps are epoch-ms `BIGINT`. The legacy Patel rows use `t-1`, `m-1`, ….
- Order `items` is JSONB `[{menuItemId, quantity, notes?}]`.
- **Walk-in orders** use a synthetic `tableId` starting with `walk-in-` and have no table row.
- Order status runs `pending → preparing → ready → served → paid`. `paid` frees the linked tables and their group, and paid orders are immutable.
- **Group seating:** `POST /api/tables/seat-group` creates one empty order shared by the tables through `group_id`, and clearing one table clears the whole group. The kitchen display hides orders that have no items.
- Saving an order with zero items deletes it and frees its table.
- `MENU_CATEGORIES` in `worker.js` must match `MenuItem['category']` in `src/types.ts` and the category lists in `App.tsx`, `OrderPanel`, `MenuModal` and `ReportsView`.

### Frontend state
- `src/api.ts`: `api<T>(path, init)` attaches the token, parses JSON and throws `ApiError` with the server's message. Use it for every API call.
- `src/context/AuthContext.tsx`: session, `userRole`, `cafeId`, `cafeName`, `createCafe`, `refreshMembership`.
- `src/context/CafeContext.tsx` (owner/counter only): tables, orders, menu and settings. Mutations call the API and then re-fetch, and live events from `useCafeLive` trigger a debounced `loadData()`. Settings saves are debounced.
- `CookDashboard.tsx` loads only `pending,preparing,ready` orders and applies live order rows directly, with no re-fetch. All updates go through `commitOrders`, which chimes when a ticket with items is new or its items change. A snapshot fetch is discarded if a live event arrived while it was in flight. Audio follows the real `AudioContext` state: the "tap to enable sound" banner returns when the browser suspends audio. It also holds a screen wake lock.
- Modals are re-mounted through `key` props instead of syncing state in effects. The React Compiler lint rules (`set-state-in-effect`, `purity`) are enforced.

### Styling
Tailwind v4 is configured CSS-first. Tokens and the `neo-brutal-btn` / `neo-brutal-card` / `neo-brutal-input` classes live in `src/index.css`. The look is Neo-Brutalist: thick black borders and hard offset shadows. `tailwind.config.js` is a leftover and is not loaded. Menu images are `.webp` files in `public/images/`.

## Database

There is no migration runner. SQL is pasted into the Supabase SQL Editor by hand:
- **Fresh project:** `schema.sql`, which is the full current schema with functions, RLS and the Realtime Broadcast trigger and policy.
- **Existing project:** the numbered files in `migrations/` in order. `004_multi_tenant.sql` added NOT NULL `cafe_id`, per-cafe settings, per-cafe unique table numbers, the owner role, RLS and the API helper functions.
- `migrations/populate_cafe.sql`: seeds the Patel's Cafe tenant (`patel-cafe-main`) with its owner accounts, tables and 101 menu items.

A schema change needs a new numbered migration, and `schema.sql` must be updated to the same end state.
